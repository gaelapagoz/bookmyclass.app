Engineering case study

Engineering BookMyClass

How a boutique-studio product became a production-oriented software platform. This page describes the technical decisions behind the application, the operational problems they address, and the current boundaries of the system.

Demonstration environment using sample data. No real bookings or charges.

Scope

Single-studio booking, commerce, customer account, teacher, and administrative workflows implemented as a modular Next.js application with PostgreSQL persistence and external payment, email, and monitoring integrations.

Engineering overview

Architecture driven by operating workflows

BookMyClass was not started as a technology exercise. It was built to manage concrete studio operations: session capacity, customer access, payments, booking status, attendance, communication, and administrative exceptions. The engineering approach keeps those decisions close to the domain services while using a deployment model that can be operated and validated without unnecessary distributed-system overhead.

Business problem

Studio operations require connected state across booking, payment, entitlement, attendance, and communication workflows.

Architecture approach

A modular monolith keeps route handling, service boundaries, data access, and external integrations in one deployable application.

Operating benefit

Release, debugging, and validation remain traceable while domain logic stays centralized and testable.

Application architecture

Modular monolith instead of premature service distribution

Decision

The application is implemented as a Next.js App Router monolith. Route handlers and server actions orchestrate requests, while business rules are grouped under service modules.

Trade-off

A single deployable application reduces coordination overhead and simplifies debugging. It does not claim multi-tenant or microservice scale; those would require explicit design work.

Data access

Prisma provides typed access to PostgreSQL. Schema and migration history record the data model for identity, catalogue, booking, commerce, ledgers, learning, support, and marketing.

Maintainability

Central service boundaries make it easier to test booking, payment, auth, dashboard, admin, cart, and email behavior without duplicating rules in UI components.

Domain complexity

Studio operations require more than a calendar

The product models a booking as part of a wider operational state. Capacity, entitlement eligibility, payment status, cancellation policy, waitlist position, customer account status, and attendance can all affect whether the studio can rely on a booking.

Scheduling

Class categories, templates, sessions, teachers, capacity, bookings, waitlist entries, and attendance records.

Access

Products, prices, entitlement rules, subscriptions, class packs, credit ledgers, wallet, and loyalty state.

Operations

Admin actions, teacher roster boundaries, inbox, learning content, documents, notes, and audit-related records.

Exceptions

Capacity limits, missing eligibility, payment completion, cancellation, waitlist promotion, unverified accounts, and failed email outcomes.

Payments and commerce

Payment completion is reconciled into local business state

Catalogue source of truth

Product + Price drives purchasable offerings. This supports recurring memberships, class packs, store items, gift cards, coupons, subscriptions, and entitlement rules without relying on page-specific assumptions.

Checkout flow

Stripe Checkout handles payment collection. Local order, payment, booking, subscription, and entitlement state is updated through webhook processing and success-page reconciliation.

Idempotency

Webhook receipts, unique identifiers, ledger keys, and cart checkout idempotency records reduce repeated processing risk for financial and entitlement workflows.

Limitation

The public case study describes architecture and behavior only. It does not expose Stripe identifiers, runtime secrets, or provider configuration values.

Authentication and security

Access control remains server-side

Client accounts

Credential sign-in, pending registration, email verification, password reset, profile update, password change, and email change verification are implemented server-side.

Role boundaries

Protected customer routes require verified users. Admin routes require admin sessions. Master Admin operations have additional server-side restrictions.

Security-sensitive flows

Stripe webhook signature verification, one-time token handling, session invalidation, rate limiting, and Sentry sanitization are part of the current implementation.

Reliable asynchronous workflows

Asynchronous work is explicit and recoverable where the product needs it

Webhook processing

Stripe events are processed with receipt tracking and reconciliation paths so local state can be updated even when browser redirect timing and webhook timing differ.

Email delivery

Lifecycle and automation-backed email uses an outbox and dispatcher path. Templates are configurable from admin automations and can be active or paused.

Scheduled maintenance

Maintenance jobs clean stale webhook receipts, expired booking drafts, cart checkout idempotency records, loyalty expirations, reminders, and reservations.

Trade-off

No separate queue or worker service is claimed. The current approach fits the single-application architecture and is documented as part of scheduled application maintenance.

Testing strategy

Validation is layered by risk

The repository includes unit, integration, UI, end-to-end, manual screenshot, performance, security, and release-validation workflows. The practical rule is to test close to the changed behavior and broaden coverage when a change crosses service or user-flow boundaries.

Unit and integration

Domain services, route behavior, auth, booking, checkout, dashboard, admin actions, and webhook paths.

UI and E2E

Rendering states, protected routes, teacher/admin boundaries, and selected critical client journeys.

Manual evidence

Operator-run UAT, smoke, security, performance, and release validation are collected when release scope requires them.

Screenshot automation

Manual Playwright automation captures client and admin demo surfaces separately from correctness-gating E2E tests.

Delivery and production operations

Release promotion is controlled and operator-approved

Runtime

The documented production model uses a cloud host, Nginx reverse proxy, PM2 cluster runtime, and Docker-managed PostgreSQL. Public static homesite assets are published separately from the application runtime.

Release flow

Releases are tag-based. The validated tag is promoted through an operator-approved workflow rather than deploying an unverified revision directly from the main branch.

Operations

Health checks, Sentry, uptime monitoring, scheduled maintenance, backups, logs, and post-deployment checks support production operation without exposing internal endpoints here.

Selected engineering decisions

Decisions connected to product and operational risk

Server-side business-rule enforcement

Booking, eligibility, payment, admin, and role-sensitive mutations are enforced in route handlers, server actions, and service modules rather than browser-only checks.

Product + Price catalogue model

Commercial offerings are modeled as products and prices, which keeps checkout behavior tied to catalogue data rather than to a specific marketing page.

Webhook plus reconciliation

Payment completion is handled through provider webhooks with success-page reconciliation as a recovery path for timing gaps.

Idempotency for workflow safety

Financial-like operations use receipts, unique keys, and ledger patterns to reduce duplicate processing when events or requests repeat.

Outbox-based email delivery

Automation-backed email is queued through an outbox and dispatcher path so delivery state can be tracked and templates can be paused.

Manual release control

Tag-based promotion and operator approval keep deployment deliberate, with UAT and production checks applied according to change risk.

Current boundaries and future evolution

Current state is intentionally separated from future direction

Current state

BookMyClass is currently a single-studio application and public demonstration platform. The public demo uses non-production or sample data and should not be read as a live customer environment.

Boundaries

Multi-tenant architecture, broader teacher functionality, no-show automation, and additional operational diagnostics are future-evolution topics unless supported by current implementation evidence.
